৩. কে কী দায়িত্বে থাকবে?

Roleসহজ ভাষায় দায়িত্বযা করতে পারবেযা করতে পারবে না
Main Adminসিস্টেমের প্রধান দায়িত্বপ্রাপ্ত ব্যক্তি।সব dashboard record দেখা; participant status update; fee/Early Bird settings; staff role assign/disable; payment review; audit log দেখা।অনুমোদন ছাড়া public live চালু করা বা ব্যক্তিগত তথ্য অপ্রয়োজনে শেয়ার করা নয়।
Payment Verifierপেমেন্টের তথ্য যাচাই করে সিদ্ধান্তে সহায়তা।Payment queue দেখা, transaction reference ও amount মিলিয়ে Verify/Reject; TEST payment review ও TEST check-in।Fee/Staff settings বা participant approval status পরিবর্তন নয়।
General Staffনির্ধারিত প্রশাসনিক সহায়তা।অনুমোদিত participant records দেখা, search/filter ও refresh।Payment queue/review, participant status পরিবর্তন, staff management বা pricing control নয়।
Event/Registration Leadদলের কাজ ভাগ, তথ্য যাচাই, deadline ও coordination।কাজের তালিকা, public announcement যাচাই, সংশ্লিষ্ট দায়িত্বপ্রাপ্তকে issue পাঠানো।নিজের dashboard permission-এর বাইরে কোনো পরিবর্তন নয়।
Teacher/Adult Supervisorপ্রাতিষ্ঠানিক অনুমতি, participant data ও real payment-এর তত্ত্বাবধান।Live launch, data handling, payment instructions ও dispute process অনুমোদন।অনুমোদন ছাড়া কোনো শিক্ষার্থীকে real payment বা sensitive data-এর দায়িত্ব দেওয়া নয়।
গুরুত্বপূর্ণ: একজনের login আরেকজন ব্যবহার করবে না। Shared password নয়। কারও কাজের অনুমতি না থাকলে Main Admin-এর কাছে পাঠাবে। Role-গুলো software permission; বাস্তব সংগঠনের পদবির বিকল্প নয়।

৪. Organizer Dashboard-এ ঢোকার নিয়ম

  1. Organizer Dashboard খুলবে।
  2. নিজের অনুমোদিত email ও password দিয়ে Sign in করবে।
  3. Login হলে উপরে নিজের email ও role দেখা যাবে। যে section দেখা যাচ্ছে না, সেটি তোমার role-এর জন্য খোলা নেই।
  4. কাজ শেষে Sign out চাপবে—বিশেষ করে shared computer হলে।

Password ভুলে গেলে

  1. Login form-এ নিজের email লিখবে।
  2. Forgot password? চাপবে।
  3. ইমেইলের নতুন reset link খুলে password reset করবে।
  4. লিংক না এলে Spam/Junk folder দেখবে; তারপরও না এলে Main Admin-কে জানাবে।
Password, OTP, reset link, API key বা database credential কাউকে পাঠাবে না—এই গাইডে বা chat-এও নয়।

৫. TEST workflow—শুরু থেকে শেষ

প্রথমবার প্রত্যেক organizer/payment verifier-কে dummy তথ্য দিয়ে এই অনুশীলনটি করা উচিত। এতে আসল participant record বা আসল টাকা জড়িত হয় না।

  1. Public Test Mode খুলবে।
  2. Division বেছে অন্তত একটি segment tick করবে। AP Debate শুধু Division C-তে নির্বাচন করা যায়।
  3. Create TEST registration চাপবে। পেজে TEST reference ও demo amount দেখাবে।
  4. Dummy payment অংশে Test bKash/Nagad/Bank বেছে transaction reference হিসেবে TEST-TXN-ABCD1234 লিখবে। Submit TEST payment চাপবে।
  5. এবার Organizer Dashboard-এ authorized Main Admin বা Payment Verifier account দিয়ে login করবে।
  6. Public TEST registrations & payments অংশে Refresh TEST queue চাপবে। তৈরি করা TEST reference দেখা উচিত।
  7. অনুশীলনে Verify TEST বা Reject TEST ব্যবহার করা যায়। Reject করলে কারণ লিখতে হবে। এটা TEST data-তেই প্রভাব ফেলবে।
  8. TEST পেজে তৈরি হওয়া token/QR value কপি করে dashboard-এর Paste TEST QR token ঘরে বসাবে। TEST check-in চাপবে।
  9. Queue refresh করে status checked_in হয়েছে কি না দেখবে।
TEST-এর নিয়ম: নিজের নাম, ফোন, email, আসল transaction ID বা ব্যক্তিগত তথ্য লিখবে না। QR camera scanning নয়—বর্তমান TEST check-in-এ token কপি/পেস্ট করতে হয়। এই TEST flow official participant record বা payment status বদলায় না।

৬. পেমেন্ট যাচাইয়ের কাজ

বর্তমান সীমাবদ্ধতা: Official public payment submission বন্ধ। Payment Verification Queue section তৈরি আছে, কিন্তু real participant payment নেওয়ার অনুমতি এখনো নেই। নিচের নিয়মগুলো official launch অনুমোদিত হওয়ার পর প্রযোজ্য হবে। এখন অনুশীলনের জন্য TEST queue ব্যবহার করবে।

Official payment চালু হলে verifier-এর নিয়ম

  1. Main Admin/Payment Verifier dashboard-এ login করবে।
  2. Payment Verification Queue refresh করবে।
  3. Registration reference, payment method, transaction reference, submitted amount এবং expected amount মিলিয়ে দেখবে।
  4. অনুমোদিত payment channel-এর record/statement থেকে transaction সত্যি এসেছে কি না যাচাই করবে। শুধু participant-এর কথার ওপর নির্ভর করবে না।
  5. সব তথ্য মিলে গেলে Verify; না মিললে Reject করে সংক্ষিপ্ত, ভদ্র ও নির্দিষ্ট কারণ লিখবে।
  6. একই transaction reference দ্বিতীয়বার এসেছে কি না সতর্ক থাকবে। সন্দেহ হলে সিদ্ধান্ত না দিয়ে Main Admin-কে জানাবে।
কখনো চাইবে না: bKash/Nagad PIN, OTP, password, card number/CVV, bank login বা account access। Transaction reference ও amount ছাড়া গোপন payment credential নেওয়া নিষিদ্ধ।

Payment status এবং Participant registration status আলাদা বিষয়। Payment verified হলেই participant-এর registration status নিজে নিজে approved হয়েছে—এমন ধরে নেওয়া যাবে না। Main Admin-এর অনুমোদিত registration process অনুসরণ করতে হবে।

৭. Participant records কীভাবে দেখবে

  1. Dashboard-এর Participant records অংশে যাবে।
  2. Search box-এ reference, নাম, email, institution, team বা segment লিখে খুঁজবে।
  3. Status filter দিয়ে All / Pending / Approved / Rejected বেছে নেবে।
  4. Team details-এর View details খুলে প্রয়োজনীয় তথ্য দেখবে।
  5. নতুন তথ্য এসেছে কি না জানতে Refresh চাপবে।
General Staff শুধু records দেখতে পারে। Participant status পরিবর্তন কেবল Main Admin করতে পারে। ভুল status দেখলে নিজে চেষ্টা না করে Main Admin-কে reference number দিয়ে জানাও।

Participant data ব্যক্তিগত। Screenshot, spreadsheet বা chat group-এ পুরো তালিকা শেয়ার করবে না। কাজের জন্য যতটুকু দরকার, ততটুকুই দেখবে।

৮. Fee ও Early Bird settings

এই section কেবল Main Admin-এর জন্য। ভুল fee দিলে অংশগ্রহণকারীদের কাছ থেকে ভুল টাকা চাওয়া হতে পারে—তাই দ্বিতীয় একজন দায়িত্বপ্রাপ্ত দিয়ে হিসাব মিলিয়ে তারপর Save করবে।

  • Segment fee schedule: segment ও division অনুযায়ী বর্তমান base fee দেখায়।
  • Early Bird deadline: নির্দিষ্ট তারিখ/সময় Save করলে discount window সেট হয়। Clear deadline দিলে Early Bird বন্ধ হয়।
  • Club member discount: eligible club member-এর জন্য নির্ধারিত ছাড়।
  • Early Bird discount: নির্দিষ্ট সময়সীমার ছাড়। বর্তমান logic অনুযায়ী Early Bird discount club-member discount-কে replace করে; দুই ছাড় একসঙ্গে যোগ হয় না।
  • Membership fee: কেবল primary registrant member নির্বাচন করলে প্রযোজ্য; non-member-এর ওপর নয়।
Public registration বন্ধ থাকা অবস্থায় শুধু fee preview দেখা যায়। Official pricing/discount পরিবর্তনের আগে লিখিত অনুমোদন ও হিসাব যাচাই আবশ্যক। Supabase-এ সরাসরি SQL edit করে fee বদলাবে না, যদি না অনুমোদিত technical maintainer নির্দেশ দেয়।

৯. নতুন Staff account যোগ/বন্ধ করা

এ কাজ Main Admin করবে; সম্ভব হলে teacher/adult supervisor-এর অনুমোদন নিয়ে।

  1. প্রথমে Supabase Authentication-এ নির্দিষ্ট ব্যক্তির নিজস্ব account তৈরি করতে হবে।
  2. Auth user-এর UUID নিতে হবে—email নয়। UUID হলো account-এর দীর্ঘ unique পরিচয়।
  3. Dashboard-এর Staff Access Management-এ UUID বসাবে।
  4. Payment Verifier বা General Staff role নির্বাচন করে Save করবে।
  5. Role list-এ account ও Active status দেখা যাচ্ছে কি না নিশ্চিত হবে।
  6. কাজ শেষ/দায়িত্ব পরিবর্তন হলে একই জায়গায় Disable access করা যাবে।
এই project-এ Main Admin role সাধারণ Staff assignment form দিয়ে দেওয়া যায় না। কাউকে Main Admin করার চেষ্টা করবে না। প্রয়োজন হলে প্রতিষ্ঠানের দায়িত্বপ্রাপ্ত adult ও technical maintainer-এর মাধ্যমে আলাদা অনুমোদিত ব্যবস্থা লাগবে।

১০. নিয়মিত রক্ষণাবেক্ষণ—কে কী দেখবে?

সময়দায়িত্বপ্রাপ্তকাজ
প্রতিদিন (registration চালু হলে)Registration Leadনতুন submission count, pending list, ভুল/অসম্পূর্ণ record চিহ্নিত; Main Admin-কে summary।
প্রতিদিন (payment চালু হলে)Payment Verifierনতুন payment queue দেখা, যাচাই, rejection reason; অমীমাংসিত case escalate।
প্রতিদিনMain AdminDashboard refresh, staff access review, payment audit log, unresolved issue ও backup/record policy তদারকি।
প্রতি announcement-এর আগেContent/Communications Lead + Main Adminতারিখ, venue, fee, deadline, contact ও registration status দুইবার মিলিয়ে public copy approve।
প্রতি সপ্তাহেMain Admin + Teacher Supervisorঅপ্রয়োজনীয় staff access বন্ধ, দায়িত্ব ভাগ পর্যালোচনা, privacy ও pending issue review।
অনুষ্ঠানের আগেOperations Leadচূড়ান্ত participant list, payment status, token/check-in পদ্ধতি, onsite device/network ও manual fallback যাচাই।

Website maintenance: Public text/design/code পরিবর্তন GitHub repository-তে হয়; Supabase-এ authentication ও database পরিচালিত হয়; GitHub Pages deployment website প্রকাশ করে। সাধারণ volunteer কোনো code/database setting edit করবে না।

১১. Official Live করার আগে বাধ্যতামূলক প্রস্তুতি

  • প্রতিষ্ঠান/শিক্ষকের লিখিত অনুমোদন এবং দায়িত্বপ্রাপ্ত adult supervisor নিশ্চিত।
  • Official organiser contact, event venue, schedule, rules ও fee final এবং যাচাই করা।
  • কোন তথ্য সংগ্রহ হবে, কেন হবে, কে দেখতে পারবে, কতদিন রাখা হবে—সহজ privacy notice তৈরি ও অনুমোদন।
  • Payment method, official account owner, payment instructions, transaction matching ও refund/dispute process লিখিতভাবে অনুমোদিত।
  • নিজস্ব dummy data দিয়ে registration → payment review → participant status → onsite check-in পুরো flow পরীক্ষা।
  • যে QR/check-in feature বাস্তবে ব্যবহার হবে, সেটি আলাদা করে test; এখনকার TEST token paste check-in-কে camera scanner বলে ঘোষণা করা যাবে না।
  • Main Admin, Payment Verifier, General Staff—প্রত্যেকের access পরীক্ষা; shared account নয়।
  • Public page-এর সব notice, contact ও date মিলিয়ে তারপরই অনুমোদিত adult/technical maintainer live launch করবে।
এখনই live registration চালু করার নির্দেশনা এই manual-এ দেওয়া হচ্ছে না। বর্তমান public intake বন্ধ। কোনো switch বা code setting নিজে বদলে real participant data সংগ্রহ শুরু করবে না।

১২. Troubleshooting—সমস্যা হলে কী করবে?

Dashboard খুলছে, কিন্তু login হচ্ছে না

Email/password ঠিক আছে কি না দেখো; Caps Lock পরীক্ষা করো। account তৈরি হয়েছে কি না এবং active EVENTORA role আছে কি না Main Admin-কে দিয়ে নিশ্চিত করো। বারবার চেষ্টা না করে password reset ব্যবহার করো।

Login হয়েছে, কিন্তু Payment/Staff/Pricing section নেই

এটি সাধারণত role permission-এর কারণে। Payment queue Main Admin/Payment Verifier-এর জন্য; Pricing ও Staff Access শুধু Main Admin-এর জন্য। নিজের role-এর বাইরে access চেয়ো না।

“No registrations have been added yet” দেখাচ্ছে

এখন official registration বন্ধ—তাই official record না থাকাই স্বাভাবিক। TEST record দেখতে Public Test Mode ব্যবহার করে TEST queue refresh করো।

TEST registration তৈরি হচ্ছে না

অন্তত একটি segment বেছে নাও; AP Debate হলে Division C বেছে নাও। Page refresh করে আবার চেষ্টা করো। একই error থাকলে সময়, error text ও page URL লিখে Main Admin/technical maintainer-কে জানাও—কোনো secret পাঠাবে না।

TEST payment reference invalid বলছে

শুধু dummy format ব্যবহার করো: TEST-TXN-ABCD1234। TEST-TXN- দিয়ে শুরু হবে; বাস্তব transaction ID দেবে না। একই reference আগে ব্যবহার করা হয়ে থাকলে নতুন dummy suffix বানাও।

TEST queue-তে record দেখা যাচ্ছে না

Payment Verifier বা Main Admin account দিয়ে login করেছ কি না দেখো; Refresh TEST queue চাপো। TEST payment submit সফল হয়েছে কি না public TEST page-এ দেখো। কিছু না হলে error text সংগ্রহ করে technical maintainer-কে জানাও।

Verify/Reject button কাজ করছে না

একবার চাপার পর অপেক্ষা করো; duplicate click করো না। Page refresh করে status দেখো। Reject করতে কারণ লিখতে হয়। Error থাকলে exact message ও record reference পাঠাও, ব্যক্তিগত তথ্য নয়।

TEST check-in হচ্ছে না

TEST page থেকে পাওয়া সম্পূর্ণ token copy করেছ কি না দেখো—শুরু/শেষে space যেন না থাকে। Dashboard-এ token paste করে TEST check-in চাপো। এই feature token paste নেয়; camera scan নয়।

Fee preview ভুল মনে হচ্ছে

Division, segment, member selection ও Early Bird deadline মিলিয়ে দেখো। Discount stack হয় না; membership fee primary registrant-এর member choice অনুযায়ী। Main Admin-কে screenshot না দিয়ে প্রয়োজনীয় selection ও displayed amount জানাও; অনুমোদন ছাড়া setting বদলাবে না।

Page পুরোনো দেখাচ্ছে / update আসেনি

একবার hard refresh করো (Windows: Ctrl+F5)। তাও না হলে GitHub Pages deployment শেষ হয়েছে কি না technical maintainer দেখবে। GitHub-এ code edit করে সঙ্গে সঙ্গে live হয়েছে ধরে নিও না।

Supabase / network / service error

Internet connection দেখো, কয়েক মিনিট পর একবার retry করো। একই error থাকলে exact error message, সময়, page এবং কোন button চাপা হয়েছিল লিখে maintainer-কে পাঠাও। API key, password, OTP বা browser session data পাঠাবে না।

ভুল করে participant status বদলে ফেলেছি

আর কোনো পরিবর্তন কোরো না। সঙ্গে সঙ্গে Main Admin-কে reference ও কী পরিবর্তন হয়েছে জানাও। Main Admin যাচাই করে সঠিক status ফিরিয়ে দেবেন; প্রয়োজন হলে audit trail/record note রাখবেন।

কাউকে account/password দিয়ে ফেলেছি

Main Admin ও adult supervisor-কে সঙ্গে সঙ্গে জানাও। account access reset/disable করার ব্যবস্থা নিতে হবে। Password বা reset link group-এ আর পাঠাবে না।

১৩. Organizing protocol—সবাই একই নিয়মে কাজ করবে

  1. একটি কাজ, একজন owner: প্রতিটি কাজের জন্য একজন মূল দায়িত্বপ্রাপ্ত এবং একজন backup থাকবে।
  2. অনুমোদন আগে: Public date, fee, venue, payment instruction বা registration opening—Main Admin ও দায়িত্বপ্রাপ্ত teacher-এর অনুমোদন ছাড়া প্রকাশ নয়।
  3. দুই ধাপে যাচাই: টাকা, fee, participant status বা public announcement পরিবর্তনের আগে আরেকজন দায়িত্বপ্রাপ্ত দিয়ে মিলিয়ে নাও।
  4. প্রমাণ রাখো: সিদ্ধান্তের তারিখ, দায়িত্বপ্রাপ্ত, reference ও সংক্ষিপ্ত note রাখো। Password/OTP বা অপ্রয়োজনীয় ব্যক্তিগত তথ্য নয়।
  5. একটি official channel: Organizer group-এ কাজের update; participant-এর private details সীমিত ও অনুমোদিত channel-এ।
  6. Issue escalation: Volunteer → Team Lead → Main Admin → Teacher/Adult Supervisor। টাকা/ডেটা/নিরাপত্তা ঝুঁকি হলে সরাসরি Main Admin ও supervisor-কে জানাও।
  7. কাজ শেষে logout: Shared computer-এ account খোলা রেখে যাবে না।
  8. কোনো অনুমান নয়: payment verified, registration approved বা check-in complete—dashboard-এ নিশ্চিত না দেখে কাউকে confirm বলবে না।

১৪. নতুন Partner/Organizer-কে handover checklist

নতুন কেউ দায়িত্ব নিলে এই তালিকা ধরে পরিচয় করিয়ে দাও।

  • □ Public Website, Test Mode ও Organizer Dashboard—তিনটি লিংক চিনেছে।
  • □ নিজের role ও সেই role-এর সীমা বুঝেছে।
  • □ নিজের account দিয়ে login/logout করতে পারে।
  • □ TEST registration, dummy payment, TEST review ও token paste check-in একবার করেছে।
  • □ Official registration এখন বন্ধ—এটা বুঝেছে।
  • □ Participant data ও payment credential-এর privacy rule জানে।
  • □ সমস্যা হলে কাকে জানাবে তা জানে।
  • □ নিজের কাজ, backup person ও reporting time লিখে নিয়েছে।
Handover সম্পন্ন বলা যাবে যখন নতুন সংগঠক নিজের ভাষায় বুঝিয়ে বলতে পারে: আমি কোন page ব্যবহার করব, আমার permission কী, কাজ শেষে কীভাবে confirm করব এবং সমস্যা হলে কাকে জানাব।
